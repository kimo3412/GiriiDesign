# 独立设计师工作室生产流程管理系统 - 数据库设计说明书

> [!NOTE]
> **毕设导师点评**:
> 本文档对应论文 **第四章 系统设计 - 数据库设计**。
> 核心技术栈：**MySQL 8.0 + MyBatis-Plus**（纯手写SQL，无任何框架自动生成）。
> 当评委问"你的数据库是怎么设计的"，请重点讲解 **4.2 模块划分** 的四大域以及 **5.1 EAV模式** 的设计意图。

---

## 1. 设计概述 (Overview)

### 1.1 设计原则
*   遵循 **第三范式 (3NF)**，消除数据冗余。
*   对于动态表单需求，采用 **EAV (Entity-Attribute-Value) 的 JSON 混合模式** 平衡灵活性与查询性能。
*   所有业务表统一前缀 `ds_` (Designer Studio)。
*   所有表统一包含审计字段：`create_by`, `create_time`, `update_by`, `update_time`, `del_flag` (逻辑删除)。

### 1.2 技术选型
*   **数据库**: MySQL 8.0 (支持 JSON 类型)
*   **字符集**: `utf8mb4` (支持 Emoji)
*   **存储引擎**: InnoDB (支持事务)
*   **ORM**: MyBatis-Plus

## 2. 概念模型与逻辑结构 (ER Schema)

系统数据划分为**四大核心域/模块**：

### 2.1 模块划分

| 模块 | 包含的表 | 职责描述 |
| :--- | :--- | :--- |
| **配置中心 (Configuration)** | `ds_category`, `ds_custom_field`, `ds_workflow`, `ds_workflow_step` | 定义"系统规则"：做什么品类、填什么字段、走什么流程。 |
| **客户中心 (Customer)** | `ds_user`, `ds_address`, `ds_portfolio` | 管理小程序用户、收货地址、展示作品集。 |
| **供应链 (Supply Chain)** | `ds_material`, `ds_bom_template`, `ds_bom_template_item` | 管理物料库存与BOM知识库。 |
| **订单中心 (Order)** | `ds_order_request`, `ds_order`, `ds_order_progress`, `ds_bom_item`, `ds_chat_message` | 驱动核心业务：意向->订单->生产->沟通。 |

### 2.2 核心关系描述 (文字版 ER 图)

1.  `ds_category` (品类) **1:N** `ds_custom_field` (动态字段)
    *   一个品类可以拥有多个定制字段。
2.  `ds_category` (品类) **1:1** `ds_workflow` (工作流模板)
    *   一个品类对应一套专属的工作流程。
3.  `ds_workflow` (工作流模板) **1:N** `ds_workflow_step` (工作流节点)
    *   一个工作流包含多个有序节点。
4.  `ds_user` (小程序用户) **1:N** `ds_address` (地址)
    *   一个用户可以有多个收货地址。
5.  `ds_user` (小程序用户) **1:N** `ds_order_request` (意向)
    *   一个用户可以提交多个定制意向。
6.  `ds_order_request` (意向) **1:1** `ds_order` (订单)
    *   一个意向转化后生成一个订单（或直接手动创建订单）。
7.  `ds_order` (订单) **N:1** `ds_workflow_step` (当前节点)
    *   订单的 `current_step_id` 指向当前所处的工作流节点。
8.  `ds_order` (订单) **1:N** `ds_order_progress` (进度记录)
    *   一个订单拥有多条进度时间轴记录。
9.  `ds_order` (订单) **1:N** `ds_bom_item` (订单BOM)
    *   一个订单关联多个物料清单项。
10. `ds_order` (订单) **1:N** `ds_chat_message` (聊天消息)
    *   一个订单下挂载所有相关的聊天记录。

## 5. 关键设计决策 (Design Rationales)

### 5.1 为什么 `custom_data` 使用 JSON 类型？ (EAV 混合模式)
*   **问题**: "服装"需要存肩宽、袖长，"插画"需要存风格、分辨率。若用传统设计，要么建 N 张品类专属表，要么预留大量 `attr1, attr2` 冗余列。
*   **方案**: 采用 MySQL JSON 类型 (EAV Hybrid Pattern)。
    *   `ds_custom_field` 表定义 Schema (元数据)。
    *   `ds_order_request.custom_data` / `ds_order.custom_data_snapshot` 存储 Payload。
*   **价值**: 兼顾关系型数据库事务能力（订单金额、状态）与 NoSQL 灵活性（定制参数）。**这是现代 Web 开发处理"动态表单"的最佳实践，也是论文的技术亮点。**

### 5.2 为什么状态流转通过配置表而非硬编码？
*   **设计**: 通过 `ds_workflow` + `ds_workflow_step` 表存储流程定义。
*   **价值**: 实现 **Data-Driven Logic (数据驱动逻辑)**。
    *   如果工作室想把"服装"流程从 4 步改成 5 步，只需在后台**改配置**，无需重新发版。
    *   这体现了系统的**高可用性**和**可维护性**，是答辩时可以重点强调的架构设计。

### 5.3 为什么使用"快照"字段 (Snapshot)?
*   `ds_order.custom_data_snapshot`: 防止客户意向中的参数在转单后被修改。
*   `ds_order.address_snapshot`: 防止客户删除地址后订单无法查看收货信息。
*   `ds_bom_item.material_snapshot`: 防止物料信息（如单价）变动后影响历史成本统计。
*   **价值**: 确保订单数据的**完整性**与**可追溯性**，符合企业级应用的设计规范。
